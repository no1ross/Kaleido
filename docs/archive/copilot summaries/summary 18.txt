1. Core Requirements

Participant must stand on its own before Orchestrator exists

Continue proving the Participant model independently.
Validate real-world behavior using the E-Commerce sample before designing Orchestrator.
Use lessons learned from Participant to simplify Queryable and eventually Orchestrator.

Metadata must be first-class

Consumers should discover capabilities from metadata endpoints, not OpenAPI schemas.
APIs should be self-describing via:
Catalog endpoints
Metadata endpoints
Execution endpoints
OpenAPI should primarily document HTTP transport, not business metadata.

Consumer-facing APIs should be consumer-friendly

Separate framework identifiers from user-facing names.
Technical names exist for routing and registration.
Display names exist for Swagger, UIs, documentation, and graph visualization.

Process and Queryable should use consistent API patterns

GET = discover / metadata.
POST = execute / query.
Consistent consumer experience across all Kaleido subsystems.
2. Architectural & Component Decisions
Registration Graph Materialization
Core discovery
The cyclic registration problem was caused by a misunderstanding between:
Graph construction
Graph projection
Key architectural distinction

ProcessStepDefinition

Mutable.
Used to build and validate relationships.
Owns graph construction.

ProcessStepRegistration

Immutable.
Runtime metadata model.
Must not participate in graph construction.
Rejected approaches
Recursive registration construction.
Mutable runtime registrations.
SetRelationships(...) style APIs.
Registration objects owning graph wiring logic.
Adopted approach
Build definition graph.
Build temporary node graph.
Build all registrations.
Wire direct relationships through lookup tables.
Project completed graph into immutable registrations.
Key insight

A registration only needs references to immediate related registrations.

It does not need recursive expansion of the graph.

Process Metadata Model
Field metadata
Moved from:
Attributes
To:
Fields

Reason:

Consumer terminology is clearer.
Better for Swagger.
Better for Angular UI.
Better for future graph/process tooling.
Constraints
Validation rules represented as constraint metadata.
Required treated as a constraint.
Constraints remain metadata only.
Metadata does not perform validation.
Shared Metadata Components

Moved toward shared abstractions:

DataTypeMetadata
ConstraintMetadata
Data type mapping helpers

These are reusable across Process and Queryable.

ProcessStepAttribute Redesign
Old model
ProcessStepAttribute(
    name,
    description,
    version)

New model
ProcessStepAttribute
{
    Name,
    Version,
    Description?,
    DisplayName?
}

Reason

Separate:

Stable technical identity
Consumer-facing display text
Documentation text
Metadata normalization

Processing now ensures:

Name         -> always populated
DisplayName  -> always populated
Description  -> always populated
Version      -> always populated


Fallbacks:

Description
    -> Description
    -> DisplayName
    -> Name

DisplayName
    -> DisplayName
    -> Name


This prevents null handling throughout the framework.

Routing

References
Internal identifiers

Use:

DisplayName


for:

Swagger
Angular UI

Consumer-facing documentation

    AcceptTermsAndConditions

Queryable API Cleanup
Discovery

Queryable followed an older OpenAPI-heavy design.

Process demonstrated a cleaner metadata-driven pattern.

Adopted Queryable pattern

Catalog:

GET /queryable


Returns registered records.

Record:

GET metadata
POST query


Named Query:

GET metadata
POST execute

Named query route redesign

Old:

GET  /queries/<query>/metadata
POST /queries/<query>


New:

GET  /queries/<query>
POST /queries/<query>


Matches Process.

Queryable Swagger Organization
Previous organization

Everything grouped by record.

Result:

Functional Records
    metadata
    query
    metadata
    query
    metadata


Became difficult to navigate.

New organization

Record:

Functional Records


Named Query:

Functional Records - Active Records

Functional Records - High Amount Records

Functional Records - Records By Category

Reason

Swagger tags are flat.

This convention simulates hierarchy.

Scales well when multiple record types exist.

Queryable Metadata Strategy
Named queries should provide descriptions

Description should explain:

What business question the query answers.


Not:

How the query is executed.


Swagger should combine:

Query Description
Operation Description

to explain both intent and behavior.
