Dependency Semantics
Confirmed Behavior

A step with multiple [DependsOnStep] attributes requires all dependencies.

Example:

SubmitOrder


depends on:

SubmitBilling
AcceptTermsAndConditions


SubmitOrder becomes available only after both are completed.

Important Distinction

Two separate concepts were identified:

Dependencies
What must happen before a step can execute.

Available Steps
What steps are valid next actions.


These are not the same thing.

Required Step Enforcement

Current framework rule remains:

requiredStep ∈ availableSteps


If a handler returns a required step that is not contained in the available-step list:

ProcessViolation
RequiredStepNotAllowed


is returned.

Architectural Decision

Required steps may only elevate a graph-valid next step.

Handlers may not create execution paths outside the defined graph.

Multiple Handlers
Final Decision

Never support multiple handlers per step.

Current behavior remains:

types.Single(...)

Rationale

A step must have exactly one handler.

Supporting multiple handlers introduces:

Ambiguity
Selection logic
Priority rules
Configuration complexity
Runtime instability

Fail-fast registration is preferred.
