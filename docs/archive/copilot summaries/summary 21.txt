1. Core Requirements

Primary Objective Remains Proving Kaleido

Goal is not e-commerce.
Goal is proving Kaleido dramatically reduces service creation time and consumer onboarding.
Service developers should focus on exposing business data rather than building dozens of custom endpoints.

Queryable Is Already Largely Validated

Successfully demonstrated:
Search
Filtering
Sorting
Paging
Search + Filter composition
Metadata-driven behavior
Search changes through attributes immediately impact behavior without changing endpoint code.

Categories Exposed the Next Major Architectural Need

Categories introduced the requirement for:
Multiple projections
Shared query context
Independent service calls
Shared application state

Category Results Must Reflect Current Product Result Set

Categories should be derived from:
Search
Filters
Named Query selection
Sort criteria
Categories should not be derived from:
Current page
Only categories with matching products should be shown.

Catalog Page Represents Shared Application State

Products and Categories are separate projections of the same page state.
The UI should orchestrate multiple service calls using a shared state model.

Runtime / Endpoint Discovery
Critical Runtime Observation

An important issue was discovered while examining generated code.

Runtime currently expects:

One endpoint
    -> One execution path
    -> One result


It does not support:

One execution
    -> Multiple view results

Correct Execution Model

Registration:

QueryContext
    ↓
Many Views


Execution:

One QueryContext
+
One Selected View
=
One Result


Example:

CatalogContext
├── Products View
├── Categories View
├── Suppliers View


Runtime executes:

CatalogContext
+
Products View


or:

CatalogContext
+
Categories View


never both.

Endpoints Become View-Based

Current direction:

Context
    -> many views


Endpoints are registered per view.

Examples:

/products

/categories


rather than directly exposing the context itself.
