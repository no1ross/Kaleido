1. Core Requirements

Repeatable step support added to Kaleido.Process

Repeatability is a step behavior, not a process state feature.
Repeatable steps may execute again regardless of prior completion history.
Initial implementation only requires:
Repeatable metadata
Consistency checker support
Availability resolver support
No execution history tracking required.
No execution count tracking required.
No process state changes required.

Repeatable is intentionally lightweight

Historical execution status does not matter for repeatable execution.
Prior results such as:
Completed
Failed
Skipped
do not prevent subsequent execution.
Repeatability means:
Execute again if requested.
Remain available when appropriate.

Framework should not own cancellation semantics

CancelOrder is simply another process step.
Framework should not:
Close processes
Terminate processes
Prevent future requests
Business meaning of cancellation belongs to the consumer.

Processes are effectively open-ended

No explicit process start concept.
No explicit process completion concept.
Processes represent durable step history.
Future actions may occur long after a process appears "finished."
Examples:
Order reinstatement
Appeals
Reconsiderations
Manual overrides
2. Architectural & Component Decisions
Repeatable Metadata
Attribute Design
Chose standalone attribute:
[Repeatable]


instead of:

[ProcessStep(..., repeatable: true)]


Reasons:

Cleaner separation of concerns.
Easier future expansion.
Behaviors evolve independently from core step metadata.
RepeatableOptions Contract
Decided to introduce:
RepeatableOptions


immediately.

Even though today it only contains:

Enabled


Reason:

Avoid future contract shape changes.
Future additions may include:
MaxOccurrences
Concurrent execution flags
Other repeatability policies
Registration Storage
Repeatability was added directly to:
ProcessStepRegistration

Not added to:
ProcessStepDefinition
ProcessStepTypeDefinition

Reason:

Repeatability is runtime metadata.
Definition graph does not require awareness of repeatability.
Consistency Checker
Historical Consistency
Repeatable steps bypass historical completion suppression.
Existing behavior:
Previously Completed
    →
Satisfied

New behavior:
Previously Completed
+
Repeatable
    →
Built

Informational Message
Added informational messaging for repeatable execution.

Concept:

Step is repeatable and remains eligible for execution.


Reason:

Improves diagnostics.
Explains why a previously completed step remains executable.
Availability Resolver Refactor
Major Architectural Change

Originally:

Current candidate
+
Request candidates
+
Completed history


were used to construct a scoped registration set.

This design failed to discover future graph nodes.

Example:

Root
 ├─ StepA
 └─ StepB


After Root:

AvailableSteps = []


because StepA and StepB were not visible.

Final Resolver Design

Adopted:

_registry.Registrations


as the candidate universe.

Availability now means:

Of all registrations,
which satisfy current rules?

Responsibility Ownership

Framework:

Evaluates graph


Developer:

Builds graph


This means:

No dependent tracking.
No reverse graph.
No graph traversal complexity.

Graph correctness becomes the consumer's responsibility.

Result

Deleted:

GetScopedRegistrations()


Completely removed scoping logic.

Availability now relies solely on:

Dependencies
AvailableAfter
AvailableUntil
Repeatable
