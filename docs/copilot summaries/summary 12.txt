1. Core Requirements

Kaleido.Process is not a workflow engine

Runtime orchestration must remain lightweight.
Process behavior is driven by metadata, planning, evaluation, and state.
Runtime should not contain business decisions or dependency logic.

State must support resumability

State is persisted after every execution pass.
A successfully completed step must never execute again.
If execution crashes after a completed step, subsequent submissions continue from persisted state.

State is not history

ParticipantContext stores only durable process continuation state.
Historical activity belongs in process events.
Step execution history was intentionally removed from state.

Request identity

CorrelationId identifies the process instance.
RequestId identifies an individual submission.
Consumers own both values and must supply them.
LastestRequestId is stored in process state for tracking.

Consumers need a complete request-level outcome

Consumer must know what happened to every submitted step.
Consumer must know overall process outcome.
Consumer must know required next step or available next steps without digging through individual step outcomes.

Historical Consistency
Previous Design

Historical consistency checker compared:

Previously completed step payload
Current request payload

And raised consistency violations when payloads differed.

New Design

Completed means completed.

Rule:

Historical Step Completed
    ->
Candidate Status = Satisfied


No payload comparison.

No history comparison.

No consistency violations.

If the step was previously completed:

Ignore whatever the consumer submitted now.

Consistency Checker Responsibility

Current behavior:

Mark previously completed steps as Satisfied
Validate dependency requirements

Possible future rename deferred until unit testing reveals true behavior.
