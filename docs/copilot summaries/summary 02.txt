1. Core Requirements

Introduce a Kaleido registration pipeline that enforces framework initialization order:

Consumers should be able to do:
services
    .AddKaleido()
    .AddQueryable()
    .AddProcess();

Consumers should not be able to call:
services.AddQueryable();

directly.

Support a shared registration context through IKaleidoBuilder.

Allow assemblies to be registered once and reused by multiple Kaleido modules:

Queryable scans assemblies for records, providers, and named queries.
Process will eventually scan assemblies for participants, capabilities, operations, etc.

Keep assembly registration explicit:

No hidden assembly discovery.
Consumers must register assemblies intentionally.

Preserve a dependency-light architecture:

Avoid introducing unnecessary framework dependencies.
Keep abstraction packages as close to dependency-free as possible.

Assembly Catalog Ownership
Core registration context owns assembly registration.

Storage Decision

Assemblies stored internally as:

Key:

assembly.FullName


Duplicate registrations are ignored via:

Public Exposure

Assemblies exposed as:

Encapsulation Goal
Only internal builder code may mutate assemblies.
Consumers and modules can only read assemblies.

Decision

Rejected

Reason:

Registration Order Requirement
Decision

Queryable requires assemblies before registration.

Invalid:

    .AddKaleido()
    .AddQueryable()
    .AddAssembly(...)


Valid:

services
    .AddKaleido()
    .AddAssembly(...)
    .AddQueryable()

    throw ...

Source vs Named Query Registration
Sources

Decision:

Only one source per record.

Examples:

    -> CustomerSource

Named Queries

Decision:

Abstractions Package Strategy
Decision

Protect dependency-free abstraction packages.

Current Position

Do not move builder infrastructure into abstractions merely to share it.

Reason:

IKaleidoBuilder depends on framework registration concepts and DI concerns.

Preferred Separation

Helper / Extension Classes
Example Discussed

Queryable

Preferred Philosophy

Wait before introducing:

Kaleido.Utilities

Kaleido.Common

Utility vs Primitive Distinction
Conclusion

EnumExtensions is a utility/helper.

It is not a primitive.

Primitives are foundational domain/value types.

Utilities are implementation helpers.

Current approach enforces:

AddQueryable()

Better diagnostics

Shared Metadata Model

Decision today:

Queryable metadata remains Queryable-specific.
Process metadata remains Process-specific.

Future validation point:

Determine whether any genuinely cross-module metadata abstractions emerge naturally.

Avoid introducing shared metadata abstractions until there is proven duplication.

Shared Helper Location

Open question:

If multiple helpers emerge:

EnumExtensions
AttributeExtensions
ReflectionExtensions
TypeExtensions


should they be extracted into a dedicated package?

Current recommendation:
