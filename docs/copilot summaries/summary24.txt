1. Core Requirements

Complete the e-commerce workflow end-to-end

Validate the full business flow:
Browse Products
    ↓
AddItemToCart
    ↓
ReconcileCartOwnership
    ↓
ProcessCart
    ↓
Order Details
    ↓
SubmitOrder

Prioritize proving the workflow before introducing additional concepts such as billing or terms acceptance.

Command/Query separation remains the primary architectural goal

Process steps mutate state.
Queryable views read state.
Process step responses should not be used as the primary mechanism for UI synchronization.
UI should reload Queryable views after process execution.

Business messaging over framework messaging

Process handlers should return meaningful business outcome messages:
Shopping cart created.
Item added to cart.
Order submitted.
Framework-generated messages (repeatable step, dependency resolution, etc.) are separate concerns.
Framework messages may eventually become optional / toggleable.

Metadata should guide consumers

Metadata is not intended to generate UI.
Metadata exists to help consumers understand:
What capability exists.
What parameters are required.
What endpoint maps to it.
What operations are available.
Metadata should remove framework implementation details from consumers.

Registry Concept

Eliminate duplicated framework identifiers from consumers.

Current:

    'orders',
    'order-details',
    request);


and

    'submit-order',
    request);


contain repeated metadata.

Key Observation

OrderDetailsView already implies:

order-details
OrderDetailsViewParameters


Likewise:

SubmitOrderStep


already implies:

submit-order

Move from:

query(
    'orders',
    'order-details',
    request);


toward:

query(
    'order-details',
    request);


or something conceptually similar.

Where metadata determines:

context
view
endpoint
required parameters


without consumer duplication.
