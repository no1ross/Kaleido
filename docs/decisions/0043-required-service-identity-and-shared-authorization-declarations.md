# 0043. Service versions are required and shared authorization declarations live in the foundation

- **Status:** Accepted
- **Date:** 2026-11-11
- **Related:** #585, #586, #588, #595; supersedes ADR 0036's optional service-version assumption and clarifies ADR 0041's foundation boundary

## Context

A service may currently omit `KaleidoServiceOptions.ServiceVersion`, creating unversioned routes and store keys. `InstanceId` is public and JSON-bindable even though it identifies one running instance and should be generated by Kaleido. The `KaleidoAuthorizationAttribute` declaration and `AuthorizationMetadata` projection were temporarily extracted to a separate low-level Registry.Next project solely to keep the capability dependency graph acyclic; they are shared by Process, Queryable and Server, not the central control registry's behavior.

## Decision

1. Every Kaleido service supplies a valid, nonblank `ServiceVersion` in code or in `Kaleido:ServiceVersion`. The version is an opaque label with the existing character/length rule. Configuration continues to override code setting by setting (ADR 0030). Do not add C# `required` to the property: a configuration server must be able to supply the value when code does not. `ScopeName` always includes the version.
2. Kaleido generates `InstanceId` once per service instance. It is internal to the foundation and its friend assemblies, not a consumer initializer or configuration setting. It remains available to the framework's registry, events and telemetry code but cannot be bound from JSON.
3. `KaleidoAuthorizationAttribute` and `AuthorizationMetadata` live together under `src/Core/Kaleido/Registry/` with namespace `Kaleido.Registry`. This is shared declaration and metadata projection, **not** central registry storage/hosting. Process and Queryable depend on Core; the empty Registry.Next shell is removed. Server owns authorization mode and service defaults; hosts/transports enforce the rules.
4. As projects are processed, default their root namespace to the project name and align declared namespaces with project-relative directories. When a public type moves folders, make and document the corresponding namespace/API change instead of retaining a mismatched compatibility namespace indefinitely.

## Alternatives considered

- Keep unversioned services for callers that do not publish HTTP routes. Rejected: version is part of every service identity and store scope, not just an HTTP route.
- Make `ServiceVersion` a C# `required` initializer. Rejected: it would prohibit configuration-only values and contradict ADR 0030's environment-controlled settings.
- Expose or bind `InstanceId` so hosts can choose it. Rejected: duplicating an instance identifier across running hosts obscures leases and observability.
- Retain a separate Registry.Next package for only two shared declaration types. Rejected: it adds a package and dependency solely to avoid putting transport-neutral shared metadata in the foundation.

## Consequences

This is a preview public API change: `ServiceVersion` is non-nullable and required at startup, `InstanceId` is internal, and the authorization attribute moves from `Kaleido.KaleidoAuthorizationAttribute` to `Kaleido.Registry.KaleidoAuthorizationAttribute` while metadata changes assembly but retains `Kaleido.Registry.AuthorizationMetadata`. Update active source/test references and PublicAPI baselines. Previously persisted unversioned Process records are not silently rewritten or deleted; their compatibility and migration are assessed when the generic Process project is reviewed. Other not-yet-migrated higher projects may require source updates in their own units under #585.
