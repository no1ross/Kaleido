# 0045. Registry publication identity and transport-neutral snapshot versions

- **Status:** Accepted
- **Date:** 2026-11-16
- **Related:** #585, #610, #611, #577, ADR 0040, ADR 0041, ADR 0043

## Context

The earlier, unreleased central Registry implementation used a JSON-serialized `KaleidoRegistry` as its store payload and a SHA-256 hash of that JSON as a registration's revision. The authority also hashed read documents into HTTP ETags. That coupled neutral authority/store identity to one encoding, conflated a service's route/state version with a particular build and gave each caller-filtered response different semantics. A compatible rebuild can add a nullable Process/Queryable field while running processes still need the same service route and `ProcessKey` scope. Process/Queryable local catalogs are CLR-rich; their portable Registry descriptions must not depend on the authority, client or ASP.NET.

## Decision

1. **Owners and direction.** `Kaleido.Registry` is lower, contracts-only and Core-only. It owns `ProcessRegistryItem`, `QueryableRegistryItem`, shared metadata, nested transport bindings and read/registration models. Generic Process and Queryable each project their own catalog once into these models with stable machine-string tokens and no `System.Type`; they retain execution behavior locally. Each installed HTTP (and later gRPC) adapter contributes only its own callable binding data. `Kaleido.Registry.Server` owns authority/store/lease/merge/cache and neutral snapshot changes; Registry HTTP server/client own their respective protocol behavior. No reverse capability or client→authority project reference.
2. **Two versions, two purposes.** `ServiceName + ServiceVersion` continues to name the logical route and durable Process state. A participant also publishes `BuildVersion`, derived once from its **deployed service entry assembly's** Product/AssemblyInformationalVersion before `+commit` metadata (for example `1.0.0-preview.616`), never from Kaleido.dll or FileVersion. It is an opaque release label, not SemVer-ordered. A new compatible build can change metadata under the same ServiceVersion; each service/version/build publication has a stable identity for the lifetime of that build. `InstanceId` remains the distinct foundation-issued running identity. Rolling deployments intersect capabilities advertised by live builds.
3. **Storage is a provider decision.** `IKaleidoRegistryStore` accepts and returns typed Registry models keyed by service/version/build; the in-memory implementation retains objects without JSON, binary serialization or hashing. Durable providers choose their own representation. The unshipped SQLite provider implementation still targets the earlier JSON/hash API and is a later #585 provider unit. There is no released SQLite Registry data to migrate; when reached, implement it against this typed contract rather than maintaining a legacy compatibility path.
4. **One neutral change signal.** The authority compares relevant active build identities and service/instance status to keep opaque capability, status, availability and combined snapshot tokens stable while those semantic views are unchanged, including across short cache rebuilds. Neither serializer bytes nor a content hash defines a publication. HTTP exposes the shared tokens as **weak ETags** and handles `If-None-Match`/`304`; a future gRPC adapter may expose the same tokens through its own protocol. A filtered response must never reuse the unfiltered token or another authenticated caller's validator, even when both see the same view: today's HTTP adapter hashes the authorized view with the validated issuer and subject. If an authenticated principal lacks a stable subject, it gets a fresh validator rather than sharing one; anonymous callers have no identity to scope. Neutralizing that authorization projection is future transport work, not a reason to leak an unfiltered token.
5. **Explicit participation.** Registry hosts run the authority without a participant. A service opts into neutral `Kaleido.Registry.Client` plus a fixed-endpoint `Kaleido.Registry.Http.Client` (or future adapter). Installed local capabilities and transport contributors are composed after DI registration; a consumer-only host hydrates without advertising an empty publication. Shared outbound HTTP request purpose/credential enforcement belongs in the common `Kaleido.Http.Client` pipeline, not in the Registry HTTP adapter or capability runtimes.

## Alternatives considered

- **Use `ServiceVersion` as every build number.** Rejected: every compatible rebuild would create a new route and Process state namespace, stranding in-flight work until old hosts stay available.
- **Hash JSON or a second binary representation inside Registry.Server.** Rejected: it couples neutral identity to a serializer and duplicates persistence/HTTP work; a provider may still choose either representation for its own storage.
- **Make every transport independently decide when the unfiltered Registry changes.** Rejected: the authority already builds one canonical view and can issue one semantic change signal.
- **Use an unfiltered ETag for caller-filtered reads.** Rejected: different callers can see different representations under one authority snapshot, so that could incorrectly answer `304` across authorization boundaries.

## Consequences

The old SHA-256 hex `Revision` format becomes an opaque semantic token; HTTP ETags are weak because timestamps can change without a semantic state change. Readers must treat versions as opaque and send the received ETag unmodified. Changing a build label is how compatible publication changes are observed; services must not reuse a label for a different published shape. The in-memory store keeps the first registration for a build and does not deep-compare later ones; a provider-owned conflict/immutability policy remains to be verified before rollout. The unshipped SQLite provider must be updated when its owner is reached; this greenfield preview has no existing released Registry rows or compatibility migration obligation. ADR 0040's versioned routes, gateway destinations, authority cache and rolling-deployment rules remain; its JSON-hash-as-publication rule is superseded here. ADR 0043's required opaque `ServiceVersion` remains the route/state identity, not the build label. Full solution/provider/MCP and Process HTTP-server migrations remain separately gated under #585.
