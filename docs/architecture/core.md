# Kaleido foundation

[`Kaleido`](../../src/Kaleido/README.md) is the lower, transport-free service baseline. `AddKaleido(configuration, options)` overlays the `Kaleido` configuration section over a copy of code-supplied `KaleidoServiceOptions`, validates it before adding services and returns `IKaleidoBuilder` carrying configuration, service options, the service collection and a deduplicated assembly scan set. It registers logging, a host-overridable `TimeProvider`, scoped correlation/caller accessors and shared CLR metadata/constraint projection (`TypeDescriber` creates `DataTypeDescriptor` and checks supported CLR types; `ConstraintMapper` projects `ValidationAttribute` to `ConstraintContract`). It does **not** register Process, Queryable, Eventing or a publisher.

## Options and correlation

Options are startup inputs: record types use `get; init;` and defaults; each owner overlays only named values from its configuration section onto a copy of code-supplied options ([ADR 0030](../decisions/0030-options-are-immutable-configuration-overrides-code.md)). Precedence is defaults, then code, then configuration. Invalid, blank, out-of-range or unreadable values fail startup rather than being silently replaced. Foundation owns `Kaleido`; Eventing owns `Kaleido:Events`; current `Kaleido:Http`, `Kaleido:Resilience`, `Kaleido:Registry:Cache`, `Kaleido:OpenTelemetry` and `Kaleido:Mcp` sections belong to their respective (not yet migrated) owners. Their Add* calls take optional code options; defaults, code and configuration retain that precedence. `MapKaleidoHttp()` has no options; `Kaleido:Clients` is not an endpoint configuration.

The scoped `IKaleidoCorrelationContextAccessor` carries request identity; callers never mint a second `RequestId` or set `X-Kaleido-*` transport headers by hand. The [correlation flow](correlation.md) describes inbound trust, caller tags and outbound propagation; [authorization](authorization.md) remains host-enforced even while the declarations/defaults still sit in foundation pending #586.

The assembly list and authorization defaults remain in `KaleidoServiceOptions` **pending the deeper foundation audit (#586)**; their presence here is not a final owner decision. `Events` was removed from those options: `AddEventing(options?)` binds `Kaleido:Events` itself. `KaleidoResilienceSettings` is currently shared by the HTTP client and Eventing, and classification inspection is shared by capability metadata and event redaction; moving either up into one consumer would reverse a dependency.

The generic `KaleidoStoreSelectionCheck` hosted service reads the **final** service collection at startup. Each owner registers a `KaleidoStoreSelectionContributor` that reports only its own stores left at in-memory defaults; a host must choose durability or call `AddInMemoryStores()` explicitly. Without Eventing, there is no outbox default to check; Process adds its own state/idempotency contribution when its steps use those stores. This neutral aggregation is transitional and will be revisited when providers and foundation are migrated. Store registration order must not change the diagnostic.

The foundation has no compile-time edge to [Eventing](events.md) or the [Process](capabilities/process.md) and [Queryable](capabilities/queryable.md) capabilities. Register those explicitly on its builder. See [dependencies](dependencies.md) for the current graph and #591 for eventual build-time architecture enforcement.
