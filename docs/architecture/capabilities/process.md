# Process capability

[`Kaleido.Process`](../../../src/Capabilities/Process/Kaleido.Process/README.md) owns step declarations/handlers, graph validation and planning, execution, recovery, resumable `ProcessContext` (`Kaleido.Process.Context`) keyed by `ProcessKey` (`Kaleido.Process.Storage`), `IProcessContextStore`/`IProcessTransactions`, Process events and `ProcessorObservability` telemetry. Its root namespace is `Kaleido.Process`, with folder-aligned subnamespaces. A **Processor** hosts and executes steps; a **Process** is one executing instance. Step names remain unmodified type names in state, events and transport requests. `ProcessContext` is current resumable state, not historical evidence; emitted events record what happened. A valid `ServiceVersion` is required for every service; persisted `ProcessKey.ProcessorVersion` and `ProcessContext.ProcessorVersion` may remain nullable for legacy reads. No stored state is silently migrated.

`AddProcess()` explicitly scans the `IKaleidoBuilder` assemblies and registers the public scoped `IProcessorRuntime` when there are steps, with typed event dispatch and a no-op transactions fallback. Console jobs, the neutral [`Kaleido.Process.Client`](../../../src/Capabilities/Process/Kaleido.Process.Client/README.md) contract and transport adapters submit typed `ProcessRequest` instances (local steps often use `ProcessRequest.ForStep`; remote mirrors use published names) and inspect `ProcessResult`/`ProcessStepResult`; the concrete `ProcessorRuntime` and local planning registries remain internal. Hosts authorize callers before invoking this neutral runtime. It does **not** register an in-memory context or idempotency store. `AddProcessEventDispatch()` registers only typed dispatch for relay-only hosts. [`Kaleido.Provider.InMemory`](../../../src/Providers/Kaleido.Provider.InMemory/README.md) explicitly offers aggregate or per-store memory choices for development; production registers durable stores. Process writes through [Eventing](../events.md)'s generic writer and owns stable `ProcessEventTypes` discriminators beside payloads (ADR 0042). `StepCandidateBuilder`, `StepCandidateValidator`, `StepCandidateConsistencyChecker`, `StepCandidatePlanner` and `StepCandidateNextStepChecker` prepare typed candidates; `ProcessorExecutor` executes accepted steps and retains recovery state after a failed save. Runtime registries remain local and project only published descriptors to the central Registry. A stale conditional save raises `ProcessConcurrencyException` (`Kaleido.Process.Exceptions`) with `pro_process_conflict`.

The public `ProcessStateSnapshot` projects current durable state without the store's optimistic-concurrency version or internal request ids; required/available steps remain **names** with any pending `InformationRequest`. `ProcessResult.ServiceVersion` names the version that executed a request. `ProcessStepHandlerResult.HandOff(target, result, stepName)` selects an existing `ProcessStepResult` and requires the target result's actual version; the origin persists `TargetProcessorName` **and** `TargetProcessorVersion` for later state reads and returns both in its result. Neither a current-version Registry lookup nor an unversioned route may silently resume that process after the target deploys a new version (#620, ADR 0040). This is transport-neutral hand-off continuation without another public response view; result/read contracts have no JSON, HTTP or callable route properties. The HTTP `ExecuteProcessRequest`/`ProcessStepRequest` and `ExecuteStepRequest<T>` input envelopes, versioned routes and Registry binding contribution belong to [`Kaleido.Process.Http`](../../../src/Capabilities/Process/Kaleido.Process.Http/README.md); [`Process.Http.Server`](../../../src/Capabilities/Process/Kaleido.Process.Http.Server/README.md) authorizes and reads JSON into typed neutral Process requests, maps process-specific conflict/recovery errors and idempotency replays, and serializes the existing generic results without central Registry participation. The neutral Process client factory accepts a current or explicitly pinned service version without choosing a route; its [`Process.Http.Client`](../../../src/Capabilities/Process/Kaleido.Process.Http.Client/README.md) adapter resolves the participant's hydrated unfiltered Registry bindings for that pinned version to call a named step ([ADR 0047](../../decisions/0047-process-response-step-identity-registry-owned-bindings.md), #619/#617/#618). Do not publish another `executeUrl` in a Process result.

## Registry catalog versus this process's current choices

The participant holds the **full hydrated Registry** of published capabilities, their metadata and versioned transport bindings. The neutral Process/Queryable clients already use that same copy for outbound routing; it is a catalog of what exists, **not** a calculation of which step one process may submit now. A caller-filtered Registry read is a presentation/discovery view for that caller (such as an agent's general tool list), not a second list of steps to offer after a Process action. Never show the full internal catalog to an untrusted caller or treat a catalog entry as permission to execute it.

A `ProcessResult` is the **current process-specific answer**. `Steps` reports the outcomes of the submitted request; it is not the choice list. `RequiredStep` is the one step the process requires, with `RequiredInformationRequest` when it is asking questions. `AvailableSteps` offers names for this process when its state is `AwaitingStepSelection`; it is empty in other ordinary states and before any step has run. On the **request that hands off**, the origin's `ProcessResult` carries the target's required/available names and `TargetProcessorVersion` as the target answered, even though the origin's state is `HandOff`. The origin's later `ProcessStateSnapshot` does not keep replaying that target choice list; a later reader needing fresh choices reads the target's state at the pinned version. The Process response never copies the full Registry metadata or embeds callable URLs.

For immediate continuation, a consumer uses only the result's current required/available **names** and its already-hydrated Registry: look up `(service, pinned version, step name)` to obtain the one published description/schema/binding and let the existing Process client make the call. There is no separate Registry-generated *next-step set* and no extra target-state or authority read just to expand the immediate hand-off response. A visible tool/description still must be authorized for the caller; the target enforces authorization on execution. General tool discovery without a current process separately uses the caller-visible Registry view, not `AvailableSteps` from an unrelated process ([ADR 0047](../../decisions/0047-process-response-step-identity-registry-owned-bindings.md), #625).

`ProcessorTransition` begins, saves state, writes the transition event to the Eventing outbox and commits, or rolls back. For atomicity, `IProcessContextStore` and the outbox must share the **same provider session/transaction**, not merely the same database; this applies to any provider technology. Register `AddContextStore<T>()` and `AddTransactions<T>()` explicitly; Eventing owns the outbox. [Foundation](../core.md) provides identity and correlation but owns none of these stores.

[`Kaleido.Process.Server`](../../../src/Capabilities/Process/Kaleido.Process.Server/README.md) independently owns neutral admission and replay under `Kaleido.Process.Server.Idempotency`: `IProcessIdempotencyStore`, `IdempotencyRecord`, `IdempotencyState`, `IdempotencyReplay` (required format identifier plus opaque bytes); [`Provider.InMemory`](../../../src/Providers/Kaleido.Provider.InMemory/README.md) owns `InMemoryProcessIdempotencyStore`. `AddIdempotencyStore<T>()` is an explicit Server registration, not part of `AddProcess()`. Transports choose scopes, request hashes and response encodings; the HTTP adapter owns a versioned replay encoding (#618) and the SQLite provider persists its opaque bytes in new schemas (#623/#587); old status/JSON replay rows are not converted. See [ADR 0044](../../decisions/0044-process-server-idempotency-ownership.md). Stable event/error/metric string values did not change with the CLR namespaces.

Consumer declarations, lookups, registration and retry expectations are in [Process authoring](process-authoring.md); the runtime-decided question/answer contract is [information requests](information-requests.md). The [Process README](../../../src/Capabilities/Process/Kaleido.Process/README.md) and scoped AGENTS rules cover implementation invariants.
