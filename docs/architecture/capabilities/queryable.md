# Queryable capability

[`Kaleido.Queryable`](../../../src/Capabilities/Queryable/Kaleido.Queryable/README.md) owns source/view declarations, metadata/discovery, validated query compilation, paging, local/delegated execution, Queryable events and `QueryableObservability` telemetry. The **source** is the identity; its query context describes how it is queried. A type is exactly one source or view capability; a view references a registered local source. The runtime (`QueryableService`, `QueryContextEngine`, `DelegatedQuerySourceEngine`) dispatches by queried type, with no lane order or fallback; `QueryRequestCompiler` and `QueryRequestValidator` validate consumer queries before both local and delegated execution. The internal source/view registries publish only the metadata needed by Registry. `IQueryContextExecutor<TView>` is a public provider seam: register an open-generic provider implementation with `services.AddSingleton(typeof(IQueryContextExecutor<>), typeof(MyExecutor<>))` so native `CountAsync`/`ToListAsync` replace the default async-enumeration/sync fallback.

`AddQueryable()` explicitly scans the `IKaleidoBuilder` assembly set, registers the public scoped `IQueryableService` and typed Queryable event dispatch; a console job or future transport adapter invokes `QueryAsync<TQuery, TResult>` with a public `IQueryRequest` and receives `QueryResult<TResult>`, while the concrete service, local catalogs and query planners stay internal. The host authorizes the source/view before invoking it, with no central Registry client needed for local execution. `AddQueryableEventDispatch()` registers only the dispatcher for relay-only hosts. Queryable's event payload and stable `QueryableEventTypes` discriminator belong here (ADR 0042), while generic envelopes/writer/relay belong to [Eventing](../events.md). Queryable does not depend on Process. HTTP converts its wire request into a CLR `QueryBody` before the runtime sees it; a delegated source (`IDelegatedQuerySource<...>` with `[QuerySource]`) returns the downstream `QueryResult<T>` without changing its total or paging semantics. `QuerySourceKind` remains service-side metadata, never a published wire kind.

`QueryBody`, `QueryFilterNode`, filters/sorts and logical operators are CLR request shapes (enums and `object?` values), not HTTP JSON; [`Kaleido.Queryable.Http`](../../../src/Capabilities/Queryable/Kaleido.Queryable.Http/README.md) owns the HTTP `QueryApiBody`/request envelopes and CLR-to-wire conversion; its later HTTP server adapter converts this body back to typed CLR filters before execution. Registry-published source/view response metadata remains a separate owner. Pageability belongs to each source/view separately and is never inherited. A pageable local source/view needs a sortable default ordering. `TotalCount` is the number of matches, not just the size of the returned page; a partial page determines it without an extra count; a full page or empty page beyond the start may require counting. The [authoring patterns](queryable-authoring.md) give source/view and provider-executor examples. The [project README](../../../src/Capabilities/Queryable/Kaleido.Queryable/README.md) and scoped AGENTS rules carry consumer usage and modification constraints. The deep review (#588) keeps public CLR request and result names stable while grouping their data-only records by request, filter and result under `Query/`. `Registry/` is the **local capability** discovery and registry-projection boundary, not the central registry: it owns type-shape checks, source/view registration and publication; `Metadata/` separates discovered registration shapes, shared query field/page contracts and published descriptions. Internal request-validator/compiler seams match their implementations. Local direct/view execution checks the request's declared parameters type against the registered capability **before** validation, source resolution or event emission, as delegated execution already does (#601).

`AddQueryable(options?)` overlays `Kaleido:Queryable:DefaultAuthorization` on a copy of code options, validates the effective rule and snapshots its role collection. An explicit source rule overrides the capability default; a view with no own rule inherits its source's effective rule. Standalone Queryable registration has an unspecified default when neither code nor configuration declares one; `AddHosting()` passes the Server-owned service default only when Queryable has no override. The [configuration inventory](../../guide/examples/kaleido-settings.jsonc) includes only sections whose owners have been processed.
