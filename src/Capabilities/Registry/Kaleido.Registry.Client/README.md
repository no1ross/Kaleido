# Kaleido.Registry.Client

This package owns the **transport-neutral participant** of the central Registry. A host explicitly opts in with `AddRegistryClient()` (normally via an installed Registry transport's participation method); local `AddProcess()` or `AddQueryable()` alone never registers remotely. It depends only on lower [`Kaleido.Registry`](../Kaleido.Registry/README.md) contracts and foundation facilities, not on the authority Server, ASP.NET, Process or Queryable runtimes.

At startup the participant combines the installed capability owners' local published Registry items and applies **only installed transport binding contributors**. The current participant registers only when a capability has an installed callable HTTP operation; a consumer-only host hydrates without advertising an empty service. A future gRPC adapter must extend that check for its own bindings. The service's `BuildVersion` is read once from its own entry assembly's Product/AssemblyInformationalVersion before `+commit`, never from Kaleido.dll. A publication is scoped by service name, state/route `ServiceVersion` and build version; instance identity comes from foundation.

The registrar retries registration, follows the authority's lease interval for local-health heartbeats, re-registers when the instance is unknown and deregisters best effort. The sync keeps a last-good Registry copy: it polls small availability at the authority's pace, reads capabilities when `CapabilitiesRevision` changes and uses conditional read tokens. Readiness requires an initial read and, for a publisher, a successful registration; a later transient failure does not undo readiness. Transport selection resolves a published service/version route from that hydrated **unfiltered** copy, not from a per-service address list. A caller-filtered view is for discovery, not routing. [`Kaleido.Queryable.Http.Client`](../../Queryable/Kaleido.Queryable.Http.Client/README.md) and [`Kaleido.Process.Http.Client`](../../Process/Kaleido.Process.Http.Client/README.md) use the internal target resolver to select their published capability bindings from this already-hydrated copy; neither makes a per-operation authority read.

**A catalog is not a process decision.** The hydrated full copy contains descriptions and bindings for every published step in each service version, independently of any one process's state. A `ProcessResult`/`ProcessStateSnapshot` supplies the names currently required or offered for *that process*; a consumer matches those names and the pinned service version against the already-held catalog to present a description or make a call. It does not fetch a second Registry "next steps" list or read target state again for an immediate hand-off result. A caller-filtered Registry read is for general discovery (for example, an agent's tool list), not a replacement for those process-specific names; do not expose the full internal copy as an unfiltered user view. The service still enforces authorization when a step runs ([Process architecture](../../../../docs/architecture/capabilities/process.md#registry-catalog-versus-this-processs-current-choices), ADR 0047).

`IKaleidoRegistryClient` is the neutral typed call contract. [`Kaleido.Registry.Http.Client`](../Kaleido.Registry.Http.Client/README.md) supplies fixed HTTP endpoint calls through the shared gateway-client pipeline; a future gRPC adapter can supply the same contract without changing this participant lifecycle. Local-only hosts need neither package in their DI graph.
