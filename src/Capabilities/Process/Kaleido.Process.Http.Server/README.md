# Kaleido.Process.Http.Server

ASP.NET Core adaptation of the local [Process runtime](../Kaleido.Process/README.md). This project maps versioned execute, per-step and state routes with the [shared HTTP server filters](../../../Transports/Http/Kaleido.Http.Server/README.md). It does **not** need a central Registry client to serve requests; an application separately opts in to publishing its [Process HTTP bindings](../Kaleido.Process.Http/README.md) when it participates in the Registry. The combined `MapKaleidoHttp()` host composition and the outbound HTTP adapter for [`Kaleido.Process.Client`](../Kaleido.Process.Client/README.md) are separate #585 owners.

## Register and map

A host registers `AddKaleido()` with `ServiceName`, `ServiceVersion` and an explicit assembly set, then `AddEventing()`, `AddProcess()`, `AddServer()`, the generic `AddHttp()`, and `AddProcessHttpServer()`. Provide `IKaleidoOutboxStore`, `IProcessContextStore` via `AddContextStore<T>()`, and `IProcessIdempotencyStore` via `AddIdempotencyStore<T>()` explicitly; these adapters do not select in-memory or production stores. The context and outbox stores need the same provider session/transaction for atomic state/event saves. If the host enforces authorization, configure ASP.NET authentication and call `UseAuthentication()` and `UseAuthorization()` before serving the mapped endpoints. Finally call public `app.MapProcessor()`; it returns a route group so ordinary host conventions can be applied. No filter or middleware is installed on unrelated host endpoints.

`KaleidoProcessHttpOptions` owns the `Kaleido:Process:Http` settings. Code-supplied settings are copied, then configuration overrides them setting by setting; validation fails at registration. `IncludeFrameworkMessages` defaults to false, and idempotency retention/lease/unknown-outcome retention default to 24 hours/5 minutes/7 days. Calling `AddProcessHttpServer()` twice is a configuration error. It requires `AddProcess()`, `AddServer()` and `AddHttp()` beforehand, but does not silently register any store or Registry participation.

## HTTP operations

| Method and route | Input | Success result |
| --- | --- | --- |
| `POST /{service}/{version}/processes/execute` | `ExecuteProcessRequest`: `steps` each with `stepName` and JSON `request` | neutral `ProcessResult` |
| `POST /{service}/{version}/processes/steps/{step}` | typed `ExecuteStepRequest<T>`: `processStep` | neutral `ProcessResult` |
| `GET /{service}/{version}/processes/{processId}` | GUID route id | neutral `ProcessStateSnapshot`, or 404 |

The input envelopes and route definitions belong to `Kaleido.Process.Http`, not generic Process. The adapter authorizes **every** submitted step before execution, rejects duplicate/unknown names and converts each JSON value to its registered CLR step type before the runtime receives a typed `ProcessRequest`; malformed fields or omitted required members return 400 without running a step. A single-step route uses its published step name. Send `X-Kaleido-Process-Id` as a request header to resume, or omit it to start a process; the response echoes the process id in that header. `ProcessResult.Steps` contains each submitted step's outcome—HTTP 200 alone does not mean that every step succeeded. When `IncludeFrameworkMessages` is false, only runtime diagnostics are removed; business messages remain. The shared `KaleidoJsonOptions` writes camelCase names and string enum values on Kaleido endpoints only.

Both results expose **step names**, never `executeUrl` or duplicate Registry metadata. `ProcessResult.ServiceVersion` is the version that ran the request; on a hand-off, `TargetProcessorName` and `TargetProcessorVersion` identify the target and its selected version. That target version persists in the origin's process state and its later `ProcessStateSnapshot`, so a client can resolve a callable binding for the **pinned** version from its already-hydrated Registry instead of drifting to a later current version. The server neither looks up the target Registry nor invents a route. Continuation names and pending information requests are filtered for the caller; a hidden required step and its questions are omitted with a `pro_not_permitted` notice. A remote target's next-step names are not reinterpreted against the origin's local step catalog.

## Authorization and errors

Per-step endpoint authorization comes from `[KaleidoAuthorization]` and the neutral `KaleidoServerOptions.AuthorizationMode`; `ZeroTrust` maps only explicitly authorized steps. Multi-step execution checks each step's declaration before anything runs. Execute and state require a caller under enforcement unless a step permits anonymous access. ASP.NET's authentication scheme answers route-level 401/403; the shared HTTP exception filter handles malformed input and authorization errors without altering host-wide middleware.

The Process HTTP exception filter translates a stale state save to 409 `pro_process_conflict`, a process still recovering to 409 `pro_process_recovering`, and a step outcome that could not be saved to 503 `pro_outcome_pending_recovery`, 409 `pro_outcome_not_saved` after a conflict, or 500 `pro_outcome_not_saved` when it was not kept for recovery. It never tells the caller to blindly retry a step that may have run. The shared JSON error shape is `{ "errors": [{ "code": "...", "message": "..." }] }`. Exceptions on unrelated host routes are the host's concern.

## Optional keyed idempotency

An execute or per-step POST may carry `Idempotency-Key`, scoped by service, **service version**, stable caller identity and the request's route, process id and raw JSON. The key is admitted before execution through the explicitly registered `IProcessIdempotencyStore`. Replaying the same completed request returns the stored HTTP answer and process-id header with `Idempotent-Replayed: true`; it does not run again. A changed request under the same key returns 422 `pro_idempotency_key_reused`. A still-running first request returns 409 `pro_idempotency_in_progress` with `Retry-After: 1`; an expired in-progress lease or uncertain outcome returns 409 `pro_idempotency_outcome_unknown` rather than risking a second execution. Keys above 200 characters, or below 16 characters for anonymous callers, are rejected with 400 `pro_invalid_idempotency_key`.

A refusal before work (including a 4xx answer) releases that admission; a successful answer completes it; a 5xx/exception after work may have run retains an unknown outcome. Finalization uses the admission's fencing id even if the caller disconnects, and a store finalization failure is logged without changing the request's answer. `Kaleido.Process.Server.Idempotency.IdempotencyReplay` remains opaque bytes plus a format identifier; this adapter alone encodes its `kaleido-process-http-json-v1` status/body payload. There is no compatibility promise for old Platform/SQLite replay rows. Idempotency cannot make a handler's writes to external systems exactly-once; such effects still need their own idempotency design.

## Tests and boundaries

The matching unit project covers route metadata, typed input, authorization, caller-filtered state/continuation, error decisions, options and idempotency lease/replay/refusal semantics. The standalone TestServer suite exercises real local Process execution, state reads, JWT roles, bad input, conflict and replay without installing a Registry participant, and checks that an unrelated route remains untouched. Generic Process owns state, runtime and event semantics; `Kaleido.Process.Server` owns neutral idempotency admission; generic `Kaleido.Http.Server` owns reusable ASP.NET filters. This project owns neither Registry authority nor outbound client routing.
