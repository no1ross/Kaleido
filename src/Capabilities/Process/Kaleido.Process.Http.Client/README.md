# Kaleido.Process.Http.Client

Outbound HTTP implementation of the neutral [`Kaleido.Process.Client`](../Kaleido.Process.Client/README.md) client/factory. Register `AddProcessHttpClient()` explicitly alongside `AddRegistryHttpParticipation()` and a shared gateway base URL (`Kaleido:BaseUrl`); neither local `AddProcess()` nor `MapProcessor()` requires either registration. The client uses the existing `Kaleido.Http.Client` named gateway credential/correlation pipeline and the participant's already-hydrated **unfiltered** Registry. It never asks the Registry authority about each Process call, reads a local Process catalog, or installs a second participation loop.

`GetClient(service)` resolves the Registry's current service version for a new process; `[FromKeyedServices("catalog")] IKaleidoProcessorClient` injects the same current-version client by service name after `AddProcessHttpClient()`. `GetClient(service, version)` pins continuation to the version returned in `ProcessResult.TargetProcessorVersion` or `ProcessStateSnapshot.TargetProcessorVersion`; use the factory rather than a keyed client for a pinned hand-off. Each call selects the matching published `ProcessRegistryItem` and exactly one HTTP operation on its `Bindings.Http`: `execute`/POST, `state`/GET, or the named step's own `execute`/POST. State uses the published `{processId}` template. Missing, ambiguous or unsafe gateway-relative bindings fail before a credential-bearing network request. Responses with a service version other than the selected version are refused rather than silently moving a running process to another deployment.

The adapter converts typed `ProcessRequest` steps to the `Kaleido.Process.Http` JSON `ExecuteProcessRequest` input envelope. Typed or by-name single-step calls send `ExecuteStepRequest<T>` using the published step binding. It reads the existing neutral `ProcessResult` or nullable `ProcessStateSnapshot`, not another response DTO. An explicit process id on an execution call wins over the front-door forwarding scope and ambient correlation; a null execution id leaves the request's process id unset, while an intentionally opened scope can still stamp its HTTP correlation header. A state GET preserves the ambient process correlation (or front-door scope), which may differ from the process id in the resource URL: reading another process does not make it the current call's process. An outbound call inside a local step stamps **this** service and executing step as per-hop caller; inbound calling-step headers are never forwarded.

Every execution POST gets a new unique `Idempotency-Key` unless the consumer supplies the same logical call's key. Only the named Process client retries keyed POSTs on transient failures or `409` with `Retry-After` while the first request is still running, under the shared `Kaleido:Resilience` attempt/delay settings. It honors the server's `Retry-After`, never retries an ordinary conflict, a key-reuse `422`, an unkeyed/unrelated POST or a request marked `NoRetry`; the shared pipeline still retries safe GET/HEAD only. The called service owns authorization, admission, replay and unknown-outcome decisions. HTTP error bodies surface through `KaleidoHttpClientException`, and an unknown process's state read returns null without altering the hydrated Registry. The server-side contract is in [`Kaleido.Process.Http.Server`](../Kaleido.Process.Http.Server/README.md); the [standalone and JWT hand-off TestServer suite](../../../../tests/Capabilities/Process/Kaleido.Process.Http.Client.FunctionalTests/StandaloneProcessClientFunctionalTests.cs) proves a real publisher, reader-only worker, hydrated Registry, current version `3` versus pinned version `2`, bounded keyed 409 retry/replay/422 and caller-token exchange (#622, #618, #620, ADR 0040/0047).
