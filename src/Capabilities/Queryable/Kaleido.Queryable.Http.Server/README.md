# Kaleido.Queryable.Http.Server

This ASP.NET Core adapter maps locally registered Queryable sources and views to versioned POST routes. It reads [`Kaleido.Queryable.Http`](../Kaleido.Queryable.Http/README.md) request envelopes and converts their JSON filter/sort/page values before invoking the public `IQueryableService`. The local [`Kaleido.Queryable`](../Kaleido.Queryable/README.md) catalog supplies source/view metadata; **no central Registry project, client or source is needed** to map or execute these endpoints.

`MapQueryable()` maps `/{service}/{version}/queryable/{source}/query` and `/{service}/{version}/queryable/{source}/{view}/query`, returning a route group for host conventions. Source and view names are lowercased CLR type names. Each typed endpoint uses [`Kaleido.Http.Server`](../../../Transports/Http/Kaleido.Http.Server/README.md) exception, correlation, JSON and caller filters. Its authorization metadata comes from the local source/view declarations and the neutral `KaleidoServerOptions`: `None` enforces nothing, `Authenticated` requires a caller plus declared roles/policy, and `ZeroTrust` omits capabilities without an explicit rule. A view can have its own rule independently of the source. The host supplies and runs its normal ASP.NET authentication/authorization middleware.

A host registers its chosen Core service identity and assembly scan, `AddEventing()` with an explicit outbox store, `AddQueryable()`, `AddServer()` and `AddHttp()` before calling `app.MapQueryable()`. The adapter does not select providers or register a central Registry client. Invalid JSON/filter values receive a structured Kaleido 400. ASP.NET's `Accepts` metadata advertises the JSON request schema and rejects other content types before the endpoint filters with a standard empty 415; unrelated host endpoints keep their own HTTP behavior. The project's unit tests cover JSON-to-CLR conversion and mapped metadata; its separate TestServer functional suite exercises a real local runtime with source/view paging, malformed filters, declared-role enforcement and unrelated endpoint isolation. The [publisher-failure cases](../../../../tests/Capabilities/Queryable/Kaleido.Queryable.Http.Server.FunctionalTests/PublisherFailureFunctionalTests.cs) verify that a Queryable response succeeds while the independently running outbox relay's publisher throws or returns a faulted task. Its [wire-contract scenarios](../../../../tests/Capabilities/Queryable/Kaleido.Queryable.Http.Server.FunctionalTests/QueryContractFunctionalTests.cs) exercise typed filter values, nested groups, search/sort/page composition, enum round trips, async sources/views, delegated-source paging passthrough and validation, neutral-query conversion and structured 400 responses through the full HTTP pipeline.

[`Kaleido.Hosting.Http`](../../../Composed/Hosts/Kaleido.Hosting.Http/README.md) now composes explicit `MapKaleido().MapQueryable()` with Process or central Registry host roles. Process HTTP execution and Registry HTTP publication remain separate. See [HTTP boundaries](../../../../docs/architecture/transports/http.md) and [Queryable authoring](../../../../docs/architecture/capabilities/queryable-authoring.md).
