# Kaleido.Queryable.Http.Client

This is the real outbound HTTP adapter for the neutral [`Kaleido.Queryable.Client`](../Kaleido.Queryable.Client/README.md) source/view client and service/version factory. A host calls `AddQueryableHttpClient()` explicitly alongside `AddRegistryHttpParticipation()` when it needs remote queries; local `AddQueryable()` and `MapQueryable()` continue to run without central participation or outbound network activity. The adapter registers a named gateway `IHttpClientFactory` client using the existing shared [`Kaleido.Http.Client`](../../../Transports/Http/Kaleido.Http.Client/README.md) caller-credential, correlation and safe-read resilience pipeline. It does not install another Registry poll/heartbeat loop.

For a standalone worker, configure `Kaleido:BaseUrl` to the gateway and call `AddKaleido(...)` with the worker's own service name/version, `AddKaleidoClientHandler<THandler>()` with its app credential, `AddRegistryHttpParticipation()` and `AddQueryableHttpClient()` in `ConfigureServices`. Build and **start the `IHost`**: `CentralRegistrySync` immediately reads availability and capabilities through the fixed Registry HTTP client, while the reader-only registrar publishes nothing. The `kaleido-registration` readiness check is healthy once both documents have been read; a query attempted before then fails locally with `registryclient_route_unavailable`. In a scope, resolve `IKaleidoQueryableClientFactory`, call `GetClient("catalog")` (or `GetClient("catalog", "1")` for a pinned version) and pass a neutral `QueryRequest` to `QuerySourceAsync<T>`. A consumer with a known service name may instead inject `[FromKeyedServices("catalog")] IKaleidoQueryableClient`, which selects the current version; use the factory for a pinned version. The already-hydrated copy is reused on each query; the hosted sync refreshes it at the authority's interval, not on each client call. This worker does **not** call `AddQueryable()`, `AddServer()` or `AddHttp()`. The [standalone functional test](../../../../tests/Capabilities/Queryable/Kaleido.Queryable.Http.Client.FunctionalTests/StandaloneQueryableClientFunctionalTests.cs) shows the exact Generic Host setup and call, including reading before hydration, readiness, no empty registration, and querying after the authority stops. The same suite round-trips decimal, enum, date, nullable and GUID record fields through a real published source, queries a projected view and retains a service's structured 400 errors. Queryable calls stamp end-to-end correlation but do not claim a calling Process step; per-hop calling-step tags belong to the Process outbound adapter.

Each query resolves the requested service's current or explicitly pinned `ServiceVersion` through `Kaleido.Registry.Client`'s target resolver, which reads the participant's already-hydrated **unfiltered Registry in memory**. It selects the matching `QueryableRegistryItem` source or view and exactly one published HTTP `query`/`POST` operation from its nested `Bindings.Http`. No route comes from a local Queryable catalog, a configured `RoutePrefix` or a per-query call to the central Registry. An absent/unread service, unsupported transport, unpublished source/view, missing/ambiguous binding or unsafe route fails locally with `registryclient_route_unavailable` **before** any credential-bearing request is sent. The path must be relative and beneath the selected version's published gateway route.

The client converts the neutral `QueryRequest`/`QueryRequest<TParameters>` through [`Queryable.Http`](../Kaleido.Queryable.Http/README.md) `ToApiBody()` into `QueryApiRequest` HTTP JSON, POSTs the published path and reads `QueryResult<T>` with shared Kaleido JSON settings. The called service remains the authorization authority; Registry caller-filtered views are discovery only and never drive route selection. Source/view names stay public strings, and missing or forbidden answers from the called service surface through `KaleidoHttpClientException` with the service's structured errors. Process-specific idempotency and calling-step tags belong to the Process client. A front door such as MCP can explicitly open the shared HTTP client's internal process-id forwarding scope around a query: the query stamps that process id on the ordinary outbound correlation header, then restores the prior context, without a separate Queryable client or Registry route ([correlation flow](../../../../docs/architecture/correlation.md)).

The lower Registry participant must first hydrate before a remote route can be resolved. This project never references Registry.Server, ASP.NET, the dead Platform project or the remote service's CLR source types. It implements [#616](https://github.com/no1ross/Kaleido/issues/616) after the neutral contracts decision ([ADR 0046](../../../../docs/decisions/0046-neutral-queryable-outbound-client-requests.md)).
